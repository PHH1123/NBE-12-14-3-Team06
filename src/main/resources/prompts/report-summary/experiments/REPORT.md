# 보고서 AI 요약 프롬프트 개선 실험 최종 보고서

- 실험일: 2026-10-18
- 대상: `ClaudeReportSummarizer` (진료 보고서 → 보호자용 요약 JSON)
- 계획서: `../prompt_readme.md`
- API 호출: **36 / 40** (1회는 코드 버그로 실패, 판정에서 제외)
- 판정: Claude (LLM) 단독. 원본 응답은 `raw/`에 모두 남아 있다.

이 문서 하나로 실험 전체(목적, 폴더 구성, 버전, 입력, 결과, v4 개선점, 권고)를 볼 수 있게 정리했다.

## 0. 한눈에 보기

| 버전 | 한 줄 설명 | 최종 판정 |
|---|---|---|
| v1 | 현재 운영 프롬프트 (한국어 지시, 예시 1개) | 기준선 |
| v2 | v1 의 지시를 영어로 + 한국어 응답 | **동등** → 채택 안 함 |
| v3 | v1 + 예시 3개 (정보 완전 / null / 키워드) | **개선** (새 입력에서도 확인) |
| v4 | 처음부터 재설계 (XML 구역, 필드 정의, 규칙의 이유, 예시 4개) | **유망, 추가 확인 필요** (표본 부족) |

**핵심 결론**
1. **치명적 왜곡은 모든 버전에서 0건이었다.** 약의 추가/중단 혼동, 용량 변경, 수치 방향 반전, 공복 조건 누락은 35번의 응답 중 한 번도 없었다.
2. **v1 의 실제 약점은 "경미한 보충"이었다.** 키워드 입력에서 `500` → `500mg`처럼 원문에 없는 단위를 붙였다 (키워드 입력 6회 중 6회).
3. **v3 가 이 약점을 없앴고, 처음 보는 입력에서도 유지됐다.** 대신 돌봄 지시가 없는 보고서에서 `caregiverNote`를 무관한 사실로 채우는 경향이 생겼다 (3회 중 3회).
4. **v4 는 v3 의 그 경향까지 없앴다** (`caregiverNote` null 2회 중 2회). 하지만 5회만 돌려 아직 확정할 수 없다.
5. **실험 중 프롬프트와 별개인 운영 버그를 발견해 수정했다** (4장). 긴 보고서에서 요약이 간헐적으로 실패하던 문제다.

**최종 권고** (9장)
1. thinking 응답 추출 버그 수정을 **먼저, 별도로 커밋**한다.
2. 운영 프롬프트는 **v3 로 바꾼다.**
3. v4 는 입력 B·C·D·E 를 3회씩(12회) 돌려 v3 와 비교한 뒤 결정한다.

## 1. 실험 개요

### 1.1 목적
동행인이 보고서를 **짧게 쓰거나 키워드만 써도**, 요약이 사실을 왜곡하거나 내용을 지어내지 않는지 확인한다. 그리고 프롬프트를 어떻게 바꾸면 이를 줄일 수 있는지 비교한다.

### 1.2 조건
| 항목 | 값 |
|---|---|
| 모델 | `claude-sonnet-5` (Spring AI 2.0.1, `max-tokens: 1024`, thinking 설정 없음 → adaptive) |
| 호출 경로 | `POST /api/dev/report-summary?version={버전}` (dev 전용, 저장 없음, 운영과 같은 `ClaudeReportSummarizer` 사용) |
| 사용자 메시지 | `다음 진료 보고서를 요약해줘.\n\n` + 보고서 본문 (코드에 고정) |
| 반복 | 같은 입력을 기본 3회 (v4 만 호출 제한으로 1~2회) |

### 1.3 진행 단계
| 단계 | 비교 | 입력 | 호출 | 목적 |
|---|---|---|---|---|
| 1단계 | v1 · v2 · v3 | B, C | 18 (+ 실패 1) | 언어 변경(v2)과 예시 보강(v3)의 효과 |
| 2단계 | v1 · v3 | D, E (새 입력) | 12 | v3 효과가 처음 보는 입력에서도 유지되는지, null 처리 |
| 3단계 | v4 | E, D, C | 5 | 재설계 버전이 v3 의 남은 약점을 해결하는지 |

### 1.4 판정 방법 (상세는 부록 B)
- 결과 1개마다 핵심 사실을 **정확 / 누락 / 왜곡**으로 판정하고, **지어내기 / 조언 추가 / 필드 오배치 / 형식 실패**를 센다.
- **지어내기**는 실제로 넣은 입력에 없는 내용이다. 사실과 맞아도(우연히 맞춘 추측이어도) 지어내기로 센다.
- **개선**: 치명 왜곡 0 · 형식 실패 0 이고, `왜곡 + 지어내기`가 비교 대상보다 **2건 이상** 적을 때. 1건 차이는 **동등**.

├── prompt_readme.md          실험 계획서 (사용자 작성)
├── v1.txt                    기준선 프롬프트 (운영 중)
├── v2.txt                    영어 지시 버전
├── v3.txt                    예시 보강 버전
├── v4.txt                    재설계 버전

    ├── REPORT.md             이 문서 (최종 보고서, 판정표·판정 기준·진행 기록 포함)

| `v1-B-1~3`, `v1-C-1~3` | 6 | 1 |

## 3. 프롬프트 버전

| 버전 | 크기 | 지시 언어 | 예시 | v1 대비 변경점 |
|---|---|---|---|---|
| v1 | 1,653 B | 한국어 | 1개 (정형외과) | - |
| v2 | 1,768 B | 영어 | 1개 (v1 과 동일, 한국어) | 지시·규칙을 영어로 번역, `Respond in Korean.` 추가 |
| v3 | 3,071 B | 한국어 | 3개 | **예시만 추가.** 지시·규칙은 v1 과 글자 하나 다르지 않음 |
| v4 | 6,579 B | 한국어 | 4개 | 전면 재설계 (7장) |

- **v2 는 v1 과 한 가지만 다르다** (언어). 효과가 없어 채택하지 않았다.
- **v3 는 v1 위에 만들었다.** 계획서의 v3 정의는 "v1·v2 중 나은 쪽 + 예시 보강"이고, v2 가 동등으로 판정돼 변경이 적은 v1 을 유지했다 (규칙 5.7).
  - 예시 1 정형외과: 정보가 모두 있는 경우 (v1 의 기존 예시)
  - 예시 2 안과: 처방·다음 방문·특이사항이 없어 null 이 나오는 경우
  - 예시 3 피부과: 키워드 입력, `세티리진 10`처럼 단위 없는 숫자를 그대로 옮기는 경우
- **v4 는 한 번에 여러 가지를 바꿨다.** 결과가 좋아도 어느 변경 덕분인지는 나눌 수 없다.
- 예시의 진료과(정형외과·안과·피부과·치과)는 모두 테스트 입력(내과·외과·영상의학과)과 다르다.

## 4. 실험 중 발견한 운영 버그

### 증상
첫 호출(v1-B-1)이 `500`으로 실패했다. 서버 로그: `응답에서 JSON 을 찾지 못했습니다. (응답 길이=0)`.

### 원인
1. `claude-sonnet-5`는 thinking 설정을 보내지 않으면 adaptive thinking 으로 동작한다. 필요하다고 판단하면 답하기 전에 생각(thinking)한다.
2. Spring AI 2.0.1 `AnthropicChatModel.buildGenerations()`는 thinking 블록을 **별도 `Generation`으로 결과 목록 앞에** 넣는다. 기본 설정에서 그 내용은 빈 문자열이다.
3. 기존 코드의 `ChatClient...call().content()`는 **첫 번째 `Generation`만** 읽는다. 그래서 thinking 이 일어난 응답에서는 빈 문자열을 받는다.
4. 짧은 입력은 thinking 없이 답해서 성공하고, 긴 입력에서만 실패한다. 그래서 **간헐적으로** 나타난다.

### 영향
운영의 보고서 요약(`ReportSummaryService`)도 같은 코드를 쓴다. 보고서가 길수록 요약이 실패해 "요약 대기"로 남을 수 있다.

### 조치 (적용됨)
`ClaudeReportSummarizer`가 `chatResponse()`를 받아, thinking 이 아닌(metadata 에 `signature`·`data` 키가 없는) Generation 의 텍스트를 골라 읽도록 수정했다. 수정 후 35회 호출이 모두 성공했다.

### 남은 위험
thinking 이 길어지면 `max-tokens: 1024`를 다 써서 JSON 이 잘릴 수 있다. 이번 실험에서는 한 번도 발생하지 않았다.

## 7. v4 개선점

### 7.1 v3 에서 바꾼 것과 겨냥한 약점

| # | 변경 | 내용 | 겨냥한 약점 | 결과 |
|---|---|---|---|---|
| 1 | **필드별 정의** | 필드마다 들어가는 것과 들어가지 않는 것을 적음. `caregiverNote`는 "의료진이 집에서 지키라고 한 생활 지침, 주의 증상, 연락 기준만"이고 "대기·검사 시간, 컨디션 같은 진료 과정 묘사는 해당 안 됨" | v3 의 `caregiverNote` 채움 (3/3) | **0/2 로 해소** |
| 2 | **null 예시 강화** | 안과 예시에 대기 시간·검사·피곤함 같은 과정 묘사를 일부러 넣고, 그래도 `caregiverNote`가 null 인 출력을 보여줌 | 같음 | 같음 |
| 3 | **규칙에 이유 추가** | 예: "추측한 단위가 틀리면 복약 사고로 이어진다", "추가·유지·중단·변경은 서로 전혀 다른 지시다" | 처음 보는 상황에서도 규칙을 일반화하도록 | 단위 보충 0/3, 약 중단 2/2 유지 |
| 4 | **아직 안 나온 위험을 규칙으로 막음** | 상대 일정을 날짜로 바꾸지 않기, 원문에 없는 `즉시`·`반드시` 붙이지 않기, 약·검사 이름 원문 표기 유지 | 예방 | 위반 0건 |
| 5 | **"처방 없음"과 "언급 없음" 구분** | 원문에 처방이 없었다고 적혀 있으면 그 사실을 쓰고, 언급 자체가 없으면 null | null 정의를 더 정확하게 | 이번 입력에는 해당 사례 없음 (미검증) |
| 6 | **맥락 설명** | 보호자가 이 요약을 사실로 믿고 복약과 진료를 챙긴다는 점, "짧고 친절한 것보다 원문에 충실한 것이 우선"이라는 점 | 판단 기준 제공 | 간접 효과 |
| 7 | **XML 태그로 구역 분리** | `context` / `input_format` / `fields` / `rules` / `output_format` / `examples` | 지시와 예시가 섞이지 않게 | - |
| 8 | **예시 4개, 한 줄 JSON 출력** | 정형외과(정보 완전), 안과(과정 묘사 + null), 피부과(키워드·단위 없는 숫자·중단), 치과(처방 없음 명시·`[연락처]` 유지) | 다양한 형태를 모방하도록 | - |
| 9 | **한국어 지시 유지** | v2 실험에서 영어의 이점이 없었고, 팀이 유지보수하기 쉬움 | - | 응답 모두 한국어 |

### 7.2 v4 의 남은 문제
- **어색한 문장 1건**: C 에서 "당화혈색소가 7.2에서 7.8로 혈당 조절이 악화되었으며"처럼 동사가 빠졌다. 의미는 맞지만, 반복된다면 문체 예시를 손봐야 한다.
- **표본 부족**: 입력당 1~2회, B(요약 입력)는 실행하지 않음. 계획서 기준(입력당 3회)에 못 미친다.
- **프롬프트 크기**: 6,579 B 로 v1 의 약 4배다. 요청마다 입력 토큰이 늘지만 요약 1건당 비용으로는 작다.
- **변경 효과를 나눌 수 없음**: 여러 변경을 한 번에 넣었기 때문이다.

## 8. 한계

1. **천장 효과**: 모든 버전이 핵심 사실을 전부 맞혔다. 테스트가 치명 왜곡을 가려내기에는 쉬웠고, 차이는 경미한 보충에서만 났다.
2. **진료 상황이 적다**: 내과·외과·영상의학과 3개뿐이다.
3. **판정자가 LLM 하나다**: 경계 사례는 판단 근거를 메모로 남겼다. 사람이 `raw/`를 한 번 확인하는 것을 권한다.
4. **v4 는 표본이 작다** (7.2).
5. **"처방 없음 명시" 처리와 `[연락처]` 유지는 테스트하지 않았다.**

## 9. 최종 권고

### 9.1 바로 할 것
1. **thinking 응답 추출 수정을 별도 커밋으로 반영한다** (4장). 프롬프트와 상관없이 운영 요약 실패를 막는 수정이다.
2. **운영 프롬프트를 v3 로 바꾼다** (`custom.ai.report-summary.prompt-version: v3`).
   - 1·2단계 모두에서 가드레일을 통과했고, 지어내기를 없앴다.
   - 바꾼 뒤 실제 보고서 작성 흐름(`POST /api/v1/applications/{id}/report`)으로 1회 확인한다.

### 9.2 다음 실험: v4 확정
- 입력 B·C·D·E 를 v4 로 3회씩 돌린다 (12회). v3 는 기존 결과를 기준선으로 쓴다.
- 확인할 것
  - `caregiverNote` null 이 E 에서 3/3 유지되는지
  - 어색한 문장이 반복되는지
  - B(요약 입력)에서 문제가 없는지
- 가드레일을 통과하고 `caregiverNote` 문제가 해소되면 v4 로 바꾼다.
- 가능하면 "처방 없음"이 명시된 입력과 `[연락처]`가 들어간 입력을 하나씩 추가한다.

### 9.3 팀에서 정할 것
- **단위 보충을 막는 게 맞는가?** `500mg`이 보호자에게 더 친절한 건 맞다. 하지만 모델이 단위를 추측하는 습관은 인슐린 단위나 μg 단위 약처럼 틀리면 위험한 경우에도 똑같이 작동한다. 이 실험은 "원문에 없는 건 넣지 않는다"를 기준으로 판정했다. 단위가 꼭 필요하다면 모델이 보충하게 하지 말고, **동행인 입력 화면에서 단위를 받도록** 하는 쪽이 안전하다.

### 9.4 선택 사항
- `max-tokens`를 1024 에서 2048 정도로 늘리거나 thinking 설정을 명시하는 것을 검토한다 (4장 "남은 위험").

|---|---|
| 정확 | 사실이 의미 그대로 들어 있다. 표현이 달라도 의미가 같으면 정확이다. |
| 누락 | 입력에 있던 사실이 결과에 없다. |
| 왜곡 | 결과의 내용이 사실과 다르다 (수치, 방향, 용량, 기간, 추가/교체 여부 등). |

### B.2 결과 전체 판정
| 항목 | 정의 |
|---|---|
| 지어내기 | 실제로 넣은 입력에 없는 내용. 사실과 맞아도 센다 (예: 단위 보충, 원문에 없는 `즉시`). |
| 조언 추가 | 원문에 없는 권고·조언 (예: "운동을 권장합니다"). |
| 필드 오배치 | 사실이 엉뚱한 필드에 들어감 (예: 소견 칸에 촬영 시간). |
| 형식 실패 | JSON 이 아니거나, 잘렸거나, 에러. |

### B.3 치명 왜곡 (하나라도 있으면 다른 점수와 관계없이 불합격)
- 약의 추가 ↔ 교체·중단 혼동
- 약의 용량·횟수 변경
- 검사 수치의 방향 반전
- 다음 방문 시점 변경, 공복 조건을 반대로 기재
- (입력 E) 판독 전인데 소견을 지어냄

### B.4 개선 판단 규칙
1. **가드레일**: 치명 왜곡 0, 형식 실패 0, 지어내기·조언 추가가 비교 대상보다 늘지 않음
2. **주지표**: `왜곡 + 지어내기`가 비교 대상보다 **2건 이상** 감소 → 개선. 1건 이하 차이 → 동등.
3. **보조지표** (주지표가 동등할 때만): 누락 수 → 일관성 → 오배치 순서로 비교
4. **동등**이면 변경이 적은 쪽을 유지한다.

### B.5 2단계 입력 E 의 `caregiverNote` 처리 (실행 전 고정)
- null → 정확
- 원문의 사실만 다시 적음 → 정확 (중복 메모)
- 원문에 없는 돌봄 지시 → 조언 추가
- 촬영 시간·컨디션만 적음 → 정확 (불필요 메모). 감점하지 않고 경향으로만 기록
