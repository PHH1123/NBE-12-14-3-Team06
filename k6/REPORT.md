# 공고 목록 성능 개선 결과 (k6)

## 1. 측정 방법
- 도구: k6. 시나리오는 `k6/baseline.js`, 공통 로그인·헬퍼는 `k6/lib/common.js`.
- 데이터: `loadtest` 프로필(`LoadTestInitData`)이 서버 시작 시 자동 생성 — 의뢰인 100 / 동행인 100 / 매칭 100쌍 / 모집 중 공고 1000건.
- 부하: 가상 사용자 50명, 30초, 1초 간격으로 `GET /posts?page=0~19&size=10`.
- 서버 지표: `/actuator/prometheus`를 1초마다 읽어 커넥션풀(active, pending), CPU 수집. 풀 최대 크기는 10.
- 신뢰도: 단계마다 같은 조건으로 3회, 첫 번째(워밍업)는 버리고 3회의 중앙값 사용.
- 환경: 맥 한 대에서 앱, DB, k6를 같이 실행. 절대값보다 전후 상대 비교용.

## 2. 문제 진단
| 확인한 것 | 방법 | 결과 |
|---|---|---|
| 캐시 동작 | 코드 확인 | `@Cacheable`에 `sync`가 없어 캐시가 비는 순간 동시 요청이 전부 DB 조회 |
| N+1 | 코드 확인 | 없음 (`JOIN FETCH p.client`, DTO는 다른 지연 로딩 연관 미사용) |
| 쿼리 비용 | `EXPLAIN ANALYZE` (공고 1116건) | 캐시 미스 1회 **102ms**. 결제 하위 쿼리(`MAX(pay2.id) WHERE post_id = ?`)가 공고마다 payment 전체를 풀스캔 (2021회 반복) |
| 기존 인덱스 | `pg_indexes` | `payment.post_id`에 인덱스 없음 (PK, 유니크만 존재) |

원인: 느린 쿼리(약 100ms) + 캐시 만료 시 동시 요청 몰림 → 커넥션풀(10개) 포화, 대기 발생 → p99 상승.

## 3. 검토한 방법과 반영 여부
| 방법 | 반영 | 이유 |
|---|---|---|
| `payment(post_id, id)` 복합 인덱스 | **반영** | 쿼리 102ms → 5ms (롤백 트랜잭션에서 사전 검증) |
| `@Cacheable(sync = true)` | **반영** | 캐시 미스 시 한 요청만 DB 조회, 나머지는 결과를 대기 |
| `post(post_status, recruit_end_at)` 인덱스 | 미반영 | 현재 규모(1천 건)에서 플래너가 사용하지 않음. 수만 건 이후 재검토 |
| fetch join / DTO 프로젝션으로 N+1 제거 | 불필요 | 이미 N+1 없음 |
| 커넥션풀 크기 증가 | 미반영 | 증상만 가리고 원인은 그대로 |

## 4. 결과 (3회 중앙값, 단계마다 서버를 새로 띄워 같은 조건으로 측정)
| 단계 | 평균(ms) | p95(ms) | p99(ms) | 커넥션 점유 평균(ms) | 풀 active 최대 | 풀 대기 최대 |
|---|---|---|---|---|---|---|
| 수정 전 | 30.4 | 126.1 | **727.5** | **176.0** | 9 | 1 |
| ① 결제 인덱스 | 8.2 | 24.5 | **91.0** | **17.7** | 10 | 6 |
| ② 인덱스 + `sync = true` | 8.5 | 18.5 | **55.0** | **17.7** | 7 | **0** |

- 커넥션 점유 평균 = 요청 하나가 DB 커넥션을 잡고 있던 평균 시간. `hikaricp_connections_usage_seconds`의 구간 처음·끝 차이로 계산.
- 인덱스로 점유 시간이 176 → 17.7ms (약 10배). `sync`는 점유 시간을 바꾸지 않고, 같은 쿼리가 동시에 여러 번 나가는 것을 막아 풀 대기를 줄인다.
- p99 727 → 55ms(약 13배), 평균 30 → 8.5ms(약 3.6배).
- 풀 대기 최대는 편차가 크다 (수정 전 1/0/34, 인덱스 1/6/11, 최종 0/0/0). 중앙값보다 "최종 단계는 3회 모두 0"이라는 점이 의미 있다.
- 점유 "최대" 시간은 서버 시작 시 시드 생성의 긴 트랜잭션(5~8초)이 섞여 있어 쓰지 않았다.
- 앞서 서버를 한 번 띄워 놓고 전체 시나리오를 돌려 얻은 수정 전 수치(p99 1,220ms, 풀 대기 14)와는 조건이 달라 값이 다르다. 이 표가 단계 간 조건을 맞춘 비교다.

## 5. 바뀐 코드
- `Payment.kt`: `@Table(indexes = ...)`로 `(post_id, id)` 인덱스 선언 (2줄 추가)
- `PostService.kt`: `searchDtos`의 `@Cacheable`에 `sync = true` 추가
- `k6/baseline.js`: `ONLY` 옵션으로 지정한 구간만 측정

운영 DB를 마이그레이션 도구로 관리한다면 인덱스를 따로 추가해야 한다:
`CREATE INDEX idx_payment_post_id_id ON payment (post_id, id);`
